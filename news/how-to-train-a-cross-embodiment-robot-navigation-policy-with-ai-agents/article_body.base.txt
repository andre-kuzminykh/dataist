# How to Train a Navigation Policy for Different Robots Using AI Agents

Navigation enables a robot to turn perception of the surrounding world and movement into autonomous task execution. Unlike locomotion, which is responsible for stable movement, navigation must continuously determine the robot’s position, account for changes in the environment, choose a route, and avoid obstacles. This article presents the COMPASS workflow: an AI agent checks dependencies, prepares scenes, starts training, diagnoses failures, and compares checkpoints. The workflow has been tested on Boston Dynamics Spot, the built-in warehouse, and the SAGE-10K scene.

Transferring this capability to a new robot or scene may require separate data, simulation resources, robot interfaces, training, diagnostics, and evaluation. Repeating this work for every “robot–scene” pair is expensive and difficult to reproduce.

An AI-agent-driven workflow reduces the amount of manual work. The developer specifies the robot, scene source, and navigation objective. A coding agent uses skills from a code repository to check dependencies, prepare resources, run validation tests, start training, identify the causes of errors, and compare checkpoints. A human confirms transitions at key stages: accepting the scene, approving the validation run in a single environment, and promoting a checkpoint.

Spot is used as the reference robot in this article. The COMPASS workflow with an AI agent is applied to the built-in scene and the SAGE-10K scene, while NVIDIA Omniverse NuRec demonstrates an option for working with reconstructed environments. The sequence includes a validation run, residual training, checkpoint evaluation, and connection to the runtime environment, including through the use of odometry.

## What Is COMPASS?

COMPASS stands for “cross-embodiment mobile policy based on residual RL and skill synthesis.” It is a system for scaling navigation transfer across different types of robots. It uses expert demonstrations collected for one robot and reapplies the navigation behavior of the pretrained NVIDIA X-Mobility policy.

For a selected robot and environment, COMPASS trains a specialized residual policy. It adjusts the base action instead of learning navigation from scratch. Later, data from several such specialists can be combined into a single policy for different types of robots.

The COMPASS policy architecture trained and evaluated by the workflow described here is shown in a diagram in the original article.

COMPASS packages the entire development process as code-repository skills. In this guide, Codex is used for development. After training, the policy and the robot controller perform navigation at runtime without the involvement of the coding agent.

## Robot, Scenes, and Odometry

The reference workflow is designed for the Boston Dynamics Spot quadruped robot.

The built-in warehouse is the primary reproducible scenario. SAGE-10K extends it to a generated scene, while NVIDIA Omniverse NuRec offers an additional path for a reconstructed target environment.

If the robot does not have compatible odometry and coordinate transforms, NVIDIA cuVSLAM can be used during deployment—a CUDA-accelerated library for visual odometry and simultaneous localization and mapping.

For another environment, use the COMPASS software stack fixed in the code repository together with the corresponding hardware settings.

## Preparing the Code Repository

Before working with a scene, prepare the code repository and give the coding agent a clear, agreed-upon sequence of actions. You need to download access-restricted resources, make the COMPASS skill available to Codex, verify the software stack, and stop at the environment-confirmation stage.

All `$compass` blocks in the guide are prompts that can be copied into the Codex chat from the root of the COMPASS code repository. They are not shell commands. In Claude Code, the same workflow is launched with the `/compass` command.

In Codex, first open the code-repository skills through `.agents/skills`, then select COMPASS with `/skills` or mention `$compass` in a prompt. Codex supports skill directories connected through symbolic links, so the current skill can remain in a supported location. In Claude Code, use `/compass` for the same process.

The AI agent can clone the code repository, build the project, download resources that do not contain secrets, and check the software stack. However, the developer must independently accept the access terms for restricted resources and enter the Hugging Face token outside the chat. The agent must not request, display, or save this token in logs.

First, clone the COMPASS code repository and complete the brief startup procedure from the COMPASS guide inside the container version fixed in the code repository. Before the first run, you must:

- accept access to the restricted Hugging Face repositories `nvidia/COMPASS` and `nvidia/X-Mobility`;
- create a Hugging Face token with read permission;
- verify that it grants access to the public gated repositories available to your account;
- pass the token only in the current shell session.

Do not paste the token into an agent prompt or add it to version control.

The resource-download stage downloads registered simulation resources to `./assets/usd/`, and the pretrained X-Mobility checkpoint to `./assets/x_mobility.ckpt`. A 401 or 403 response usually means that repository access has not been configured completely or that the token lacks sufficient permissions. Fix authentication first, and only then investigate Isaac Lab.

Before moving to the next stage, each stage must leave verifiable evidence. For every confirmation point, determine:

- whether the required inputs are present;
- whether the expected output files have appeared;
- whether any unresolved errors remain;
- whether there is sufficient evidence to continue.

After launching the container, open the AI agent in the root of the code repository and describe the robot, scene, expected navigation result, and confirmation points. For the baseline scenario, copy the prepared prompt from the guide into the agent chat.

The `$compass` skill checks the requested workflow against the contents of the code repository and launches the required validations. If a run fails, `$compass-doctor` performs a read-only status check and reports likely causes without changing the environment without permission.

## Preparing the Scene

COMPASS supports three scene sources:

- the built-in COMPASS warehouse;
- the generated SAGE-10K scene;
- an environment reconstructed with Omniverse NuRec.

Each option requires its own checks for registration, occupancy maps, and scene confirmation before training begins.

### Built-in Warehouse

For the first reproducible run, the registered `combined_multi_rack` warehouse is recommended. The robot, scene, and occupancy map have already been added to the system, making this option suitable for validating the installation before connecting a new scene.

Copy the prompt into the AI agent. It launches the baseline scenario and stops the process after the validation run in a single environment.

### SAGE-10K Scene

The SAGE-10K dataset contains 10,000 generated rooms across 50 types. It is a scene dataset, not a policy or a simulator. Each scene includes geometry, materials, layout metadata, and a preview.

Living-room and warehouse scenes are prepared in the same way, so downloading the entire dataset is unnecessary: simply select a suitable option.

SAGE-10K provides two points for human confirmation. First, open the converted USD file in NVIDIA Isaac Sim and check the geometry, materials, scale, and collision meshes. After registering the scene and creating the occupancy map, confirm the preview in a single environment before starting full training.

An occupancy map shows free and blocked space. It is used to select valid initial robot positions and navigation goals.

The guide recommends copying a prompt into the agent chat that selects a scene and stops at both confirmation points.

### NuRec Reconstructed Environment

Omniverse NuRec is suitable when COMPASS needs to be fine-tuned and evaluated in a reconstructed environment where the robot will operate. NuRec converts stereo RGB images into a reconstruction suitable for Isaac Sim. It includes consistent visual geometry, collision meshes, and, when necessary, additional scene elements.

The documented COMPASS path for NuRec includes registering the rendered scene, checking the supplied occupancy map and origin conventions, verifying clearances for the robot, and running a validation test in a single environment before training.

NuRec is presented in this article as an additional option. The practical training section continues with SAGE-10K in order to take one scene through the complete process—from preparation to evaluation.

For a reconstructed environment, use the COMPASS workflow for NuRec together with the NVIDIA Isaac Sim NuRec guide. This guide, including its living-room example, describes scene preparation, training, evaluation, export, and deployment with ROS 2.

Copy a separate prompt into the agent chat to prepare the registered NuRec scene. The process then stops before training begins.

## Validation Run

Once the selected scene is available to COMPASS, run a preview in a single environment before scaling up training. For SAGE-10K, the visual inspection and scene-registration confirmation must be completed first.

Make sure that:

- Isaac Sim launches;
- the scene loads;
- Spot appears in a valid location;
- camera images are available;
- the robot follows the policy commands;
- the robot does not hit objects, fall, or produce unresolved simulation errors.

The AI agent should compile a brief summary of the preview logs and visual evidence, identify possible blocking issues, and stop until a human confirms the result.

Proceed to residual training only after the scene, robot, observations, and action interface work together as expected.

## Residual Training

At this stage, the pretrained X-Mobility policy is adapted to the selected robot and scene. Start residual reinforcement learning, monitor the process, save suitable checkpoints, and prepare evidence for subsequent evaluation.

After the validation run is approved, the agent can start the standard residual reinforcement-learning workflow. The example uses Spot and the built-in warehouse. When working with an SAGE-10K scene, replace the environment key with the registered key for that scene.

Residual training may continue for a long time. The agent should run it in a persistent session or through a managed scheduler. Logs and checkpoints should be saved to the configured directory, and progress should be reported without requiring an interactive session to remain open.

Before training begins, record:

- the launch command;
- the code-repository revision;
- the scene key;
- the configuration;
- the checkpoint-save interval;
- the stopping conditions.

If the process is interrupted, check the integrity of the latest checkpoint and clarify the supported options for resuming training.

Choose the `--num_envs` parameter based on the available GPU memory. Use only one environment for the validation run. During training, monitor:

- reward components;
- progress toward the goal;
- contacts and falls;
- episode terminations;
- performance;
- GPU memory usage.

Save checkpoints periodically and evaluate them under identical conditions. Do not assume in advance that the final iteration will be the best one. COMPASS also supports distributed training across multiple GPUs for larger runs.

Training time depends on the hardware, scene complexity, number of environments, and stopping conditions.

When failures occur, first use the COMPASS diagnostic workflow rather than immediately changing the environment or training configuration. The type of problem determines the next direction of investigation:

- authentication errors—check Hugging Face access;
- scene-loading and collision errors—review scene preparation;
- camera or action-interface errors—review the validation-run stage;
- memory errors—adjust the number of environments or the multi-GPU training configuration.

Save the training configuration, launch command, code-repository revision, scene registration, occupancy map, validation-run evidence, logs, checkpoints, and artifact manifest.

Developer confirmation is required before changing dependencies, scene resources, rewards, or training settings.

## Checkpoint Evaluation

After training, determine whether a residual checkpoint is ready for promotion. To do this, compare the pretrained base policy and residual-training candidates under identical conditions.

Standard COMPASS evaluation considers:

- the goal-achievement rate;
- the fall rate;
- route-completion time.

Additional data—such as progress toward the goal, contact behavior, timeouts, or command stability—must be labeled as derived analysis or as the results of user instrumentation.

A checkpoint may be packaged only after comparable results meet the project’s navigation and safety requirements and a human has approved the packaging step.

The guide includes an example evaluation prompt. Adapt it to the specific robot, scene, set of checkpoints, and required evidence.

## Connecting to the Robot

After development is complete, connect the trained policy to the robot’s runtime environment. The AI agent coordinates development and validation, but it does not control the robot during operation.

The COMPASS resource-download stage retrieves the pretrained X-Mobility checkpoint used for the validation run and residual training. Training itself creates a residual checkpoint for the selected robot and scene.

Export and deployment prepare the trained policy for inference. They do not turn the base and residual policies into two separate ROS 2 components that the developer must connect manually.

In the reference ROS 2 integration, the `compass_inference` component receives:

- images from the front camera;
- a navigation goal or route;
- the robot velocity calculated from odometry.

It uses these inputs to construct the inputs to the exported policy and publishes forward linear-velocity and angular-velocity commands to `/cmd_vel`.

The recurrent state and previous action remain internal implementation data for inference and are not passed into the ROS 2 integration as external inputs.

For the target deployment, check coordinate frames, update rates, normalization, command limits, stop behavior, and the physical robot controller.

## Odometry with cuVSLAM

The cuVSLAM library is needed when the robot requires camera-based state estimation in an environment with unavailable or unstable GPS and does not have compatible, validated odometry and transforms.

cuVSLAM odometry can be used by the COMPASS navigator, but the cuVSLAM map is not passed to the navigation policy as an input.

cuVSLAM does not participate in COMPASS policy training and does not require an agent skill. It should be run as a separate ROS 2 component with compatible versions, and its odometry should be connected or remapped to `/chassis/odom`. The required `odom`–`base_link` transform must also be provided, and calibration, timestamps, topic names, and coordinate-frame conventions must be checked.

The additional `$cuvslam-onboard` and `$cuvslam-troubleshoot` skills can help configure and diagnose this state-estimation component during development.

## New Robot Type

If the robot has not yet been registered, the `$compass-newembodiment` skill guides the developer through robot configuration, environment registration, action mapping, and a visual validation run in a single environment.

Connecting a new robot type is a separate engineering task from training a specialist for a robot that is already registered. The same sequence of checks and confirmations is used.

## Workflow Boundaries

The guide ends at checkpoint evaluation. Export to ONNX, JIT, or TensorRT, ROS 2 integration, and deployment on physical hardware require separate checks for the specific robot and runtime environment.

Scene quality, training duration, and checkpoint results depend on the robot type, environment, reward structure, and available computing resources. Therefore, the workflow does not define a single universal success threshold.

The recommended approach is to begin with the reference scenario and then add one component at a time.

The corresponding COMPASS resources are listed at the end of the guide for reproducing and extending the process.
