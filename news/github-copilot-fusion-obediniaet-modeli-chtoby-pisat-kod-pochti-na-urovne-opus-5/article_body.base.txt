# GitHub Copilot Fusion приблизился к Claude Opus 5.5, снизив расходы на задачу вдвое

На конференции GitHub Universe 28 октября компания показала систему, которая распределяет запросы между моделями и координирует их работу в рамках одной задачи.

В тестировании Artificial Analysis, опубликованном 28 октября, Fusion Max тратил в среднем $5,59 на задачу. Claude Code с Claude Opus 5.5 в режиме Max обходился в $11,42. Это примерно на 51% дороже; в агент для программирования Index Fusion отстал всего на два балла.

Результаты дают GitHub независимую оценку, подкрепляющую аргумент компании: грамотный выбор моделей может удешевить разработку с помощью ИИ.

По данным GitHub, Fusion Max также выполнял тестовые задачи примерно на 40% быстрее, чем конфигурация Claude Code.

Гендиректор Microsoft Сатья Наделла говорил о возможной экономии до 77%. Но эта цифра относится к отдельной оценке самой компании, а не к среднему результату Artificial Analysis. В аргументации GitHub на первый план выходит стоимость выполнения задачи, а не цена отдельной базовой модели.

В интервью VentureBeat директор по продуктам GitHub Марио Родригес объяснил, что Fusion должен упростить выбор модели и снизить стоимость выполненной работы. Для корпоративных клиентов важно понять, превращается ли удешевление инференса в сокращение общих трудозатрат на разработку.

## Fusion координирует модели

Fusion оценивает задачи, связанные с рассуждением, генерацией кода, отладкой и использованием инструментов, а затем решает, передать запрос одной модели или скоординировать несколько. Система объединяет возможности, разработанные для исследовательского проекта GitHub Project HydraFusion, и функцию автоматического выбора модели.

Родригес объяснил, что Fusion — не отдельная модель, а система координации, работающая во время выполнения. Она может как направлять отдельные запросы, так и организовывать несколько обращений к моделям, чтобы завершить задачу.

GitHub изменила и то, как разработчики используют Fusion. Вместо отдельной модели в списке теперь доступен режим с разными уровнями усилий: стандартным, высоким и максимальным.

1. **Standard** выбирает универсальные модели для повседневного программирования.
2. **High** предназначен для более сложной работы.
3. **Max** рассчитан на самые трудные задачи.

Система использует три схемы выполнения:

1. **Single** сразу передаёт задачу одной модели.
2. **Cascade** начинает с менее дорогой модели и решает, принять её результат или передать задачу более мощной.
3. **Critique** поручает одной модели подготовить ответ, другой — проверить его, а первой — исправить результат. Эти схемы описаны в документации GitHub к запуску.

Родригес пояснил, что в режиме Single запрос сразу направляется модели, которую система считает подходящей для задачи. В Critique более мощная модель участвует в проверке, но не обязательно выполняет каждый этап. Цель, по его словам, — позволить разработчикам сосредоточиться на том, что должна делать программа, не заставляя их постоянно выбирать модель.

Artificial Analysis обнаружила в наборе Fusion модели Anthropic и OpenAI: Claude Opus 5.5, Claude Sonnet 5.5, GPT-6 Astra и GPT-6 Sol. Конкретный выбор зависит от запроса и политик организации.

## Что показали независимые тесты

Artificial Analysis проверила режим Fusion Max через GitHub Copilot CLI в агент для программирования Index v2.0. В индексе поровну учитываются три оценки программирования.

Fusion набрал 60 баллов. Claude Code с Opus 5.5 Max получил около 62. Конкурирующая система координации Devin Fusion, использовавшая Opus 5.5 Max и GPT-6 Luna High, тоже набрала 62 балла при средней стоимости $8 за задачу.

По расходам Fusion показал $5,59 за задачу против $11,42 у Claude Code с Opus 5.5 и $8 у Devin Fusion. Artificial Analysis также оценила объём работы Fusion в 7,2 миллиона токенов на задачу — примерно вдвое меньше, чем у конфигурации Claude Code с Opus 5.5, и примерно на 30% меньше, чем у Devin Fusion. Это указывает, что экономия связана хотя бы отчасти с меньшим объёмом работы моделей, а не только с более дешёвыми токенами.

По отдельным тестам результаты различались. В Terminal-Bench 4.0 Fusion оказался впереди систем, рассмотренных в отчёте, с результатом 71 балл. В FrontierCode — тесте изменений в репозиториях — он набрал 51 балл, уступив Claude Code с Opus 5.5, у которого было 56, и Devin Fusion с 54 баллами. В тесте вопросов и ответов по репозиториям SWE-Atlas-QnA-AA Fusion получил 57 баллов. Близкий общий результат не означает, что Fusion выигрывает при любом типе задачи по программированию.

Указанная стоимость относится к тестам, а не к опубликованной оценке расходов конкретной компании по новой схеме покупки ИИ-кредитов GitHub. В статье Artificial Analysis также нет данных о времени выполнения каждой задачи, которыми можно было бы подтвердить заявление GitHub об экономии 40%. Это сравнение приводит сама GitHub; независимая проверка подтверждает показатели производительности, расхода токенов и стоимости.

Оценку экономии до 77% нужно рассматривать отдельно. Как сообщил Кен Йенг в The AI Economy, во внутренних тестах GitHub с бенчмарком DeepSWE и агентской системой Copilot режимы Fusion High и Max превзошли сопоставимые конфигурации передовых моделей максимум на 8,7 балла по завершению задач. Расчётная стоимость при этом снизилась на величину до 77%.

В этом сравнении использовались другие условия тестирования, а 77% — максимальное заявленное снижение. Эти результаты нельзя напрямую сопоставлять со средней экономией примерно в 51% у Artificial Analysis при сравнении с Opus 5.5. Данные о конфигурациях DeepSWE и стоимости отдельных задач в рассмотренных материалах отсутствовали.

Деловое обоснование GitHub зависит от того, означает ли экономия на тесте снижение общих расходов на выпуск ПО. Командам по-прежнему нужно учитывать проверку людьми, ошибки, повторные попытки, интеграцию и работы по безопасности после ответа агента. Вице-президент Microsoft по направлению CoreAI Джей Парикх в объявлении на GitHub Universe подчеркнул, что результатом должна быть выполненная работа, а не просто дополнительный код.

## Оплата моделей, временная скидка и корпоративный тариф

Copilot Fusion доступен всем подписчикам GitHub Copilot в VS Code, приложении Copilot, Copilot CLI и средах разработки JetBrains. GitHub планирует добавить поддержку других клиентов. Компания сообщает, что пользователи платят за каждую модель, к которой обращается Fusion, по её стандартному тарифу.

Подписчикам платных планов Copilot временно предоставляют скидку 30% на стоимость моделей при работе с Fusion. Эта акция не связана с экономией на задаче, которую измеряли в бенчмарках.

Родригес связал экономичность Fusion с маршрутизацией запросов и координацией моделей, а не с тем, что GitHub компенсирует расходы на дорогие запросы. Однако это объяснение не раскрывает маржу GitHub и не гарантирует, что любая задача обойдётся дешевле, чем при ручном выборе одной модели.

Отдельно GitHub предлагает некоторым клиентам GitHub Enterprise Cloud новый способ покупать Copilot. Компаниям, работающим через менеджеров по работе с клиентами GitHub или Microsoft, могут включить доступ и списывать расходы на использование ИИ из корпоративного бюджета. Им не придётся покупать дополнительную подписку Copilot на каждого лицензированного пользователя Enterprise.

По опубликованным условиям такие пользователи не получают ежемесячный запас ИИ-кредитов на каждого сотрудника: оплата по факту начинается с первого запроса.

У этой схемы есть практическое различие. Автодополнение кода и предложения следующего изменения остаются доступны, даже если бюджет на ИИ исчерпан. Copilot Chat, проверка кода и облачный Copilot требуют доступного бюджета.

Подписки Copilot Business и Copilot Enterprise остаются в продаже, а самостоятельное подключение новой схемы будет появляться поэтапно. GitHub также указывает тариф Copilot Standalone — $10 на пользователя в месяц для пользователей корпоративных аккаунтов без лицензии GitHub Enterprise.

Опубликованные условия объясняют порядок доступа и оплаты, но в рассмотренных материалах нет примера, который показывал бы ежемесячный расход ИИ-кредитов типичной команды разработки. Покупателям придётся сравнивать фактическое использование и ограничения бюджета с действующими тарифами на основе числа лицензий.

## Проекты и непрерывные сессии

GitHub расширяет Copilot за пределы подсказок кода: с его помощью разработчики могут планировать работу, поручать задачи агентам и проверять результаты. В приложении Copilot доступны спецификации, обсуждение дизайна и анализ телеметрии наряду с программированием.

Copilot Projects позволяет запускать параллельные облачные сессии агентов в нескольких репозиториях и отслеживать их в одном интерфейсе.

Непрерывность сессий позволяет переходить между приложением Copilot, сайтом, командной строкой и VS Code, сохраняя контекст того же облачного агента.

Родригес подтвердил, что работу можно продолжать на разных устройствах, включая мобильные. Это может пригодиться командам, если агенты продолжают работать после того, как разработчик закрыл ноутбук или переключился на другую часть проекта.

Родригес также представил эти изменения как способ сделать разработку доступнее для непрофессионалов, не ограничивая опытных инженеров. По его словам, GitHub хочет снизить порог входа в создание программ и дать специалистам больше возможностей. Он указал на сообщество платформы, объединяющее более 225 миллионов разработчиков.

Родригес также рассказал о работе GitHub над сохранением полезной информации из сессий с агентами и её включением в знания организаций о технических областях, рабочих процессах и практиках разработки.

GitHub расширяет и Copilot Automations. Команды смогут запускать процессы с агентами вручную, по расписанию или в ответ на события, а затем проверять и утверждать предлагаемые улучшения на основе прошлых результатов. Требование одобрения сохраняет за человеком право решать, менять ли инструкции рабочего процесса.

## Корпоративные настройки моделей и качество кода

Динамический выбор моделей ставит вопрос об управлении: если система сама выбирает поставщиков, сможет ли компания ограничить список разрешённых моделей?

В примечаниях к выпуску Fusion GitHub указывает, что система соблюдает политики моделей на уровне предприятия и организации. Администраторы могут видеть список моделей, доступных Fusion, отключать отдельные модели именно для Fusion и задавать уровень усилий по умолчанию. На вопрос о видимости используемых моделей Родригес ответил утвердительно, но интервью не уточнило, какие именно сведения будут доступны для аудита каждого запроса.

Родригес также отметил, что с ростом объёма разработки с помощью ИИ возрастает потребность в проверке и безопасности. GitHub добавила максимальный уровень проверки кода Copilot — отдельно от Fusion Max. Также доступны уровни Lite и Balanced.

По заявлению компании, новый уровень получил лучший F1-показатель по серьёзным проблемам в ReviewBench, но в объявлении на GitHub Universe подробной разбивки результатов нет. Родригес также рассказал о проверке безопасности с помощью ИИ, предназначенной для обнаружения уязвимостей, которые могут пропустить традиционные методы статического анализа.

## Больше агентов — больше инфраструктуры

GitHub расширяет инфраструктуру, на которой работают её продукты. В объявлении на GitHub Universe компания сообщила, что в 2026 году добавила 160 петабайт высокоскоростного хранилища, 4 миллиона ядер процессора и сетевую пропускную способность 50 терабит в секунду.

Компания также переходит к развёртыванию Azure в нескольких регионах и рассчитывает завершить этот переход в начале 2027 года. Кроме того, GitHub меняет архитектуру Git: вычисления отделят от хранения данных, чтобы сократить издержки на координацию.

Родригес связал эту работу с ростом числа чтений и записей в репозиториях из-за агентов. Когда автоматизированные сессии чаще получают код, меняют файлы и отправляют изменения, инфраструктуре разработки приходится обслуживать больше параллельной работы.

Для корпоративных клиентов ценность Fusion будет зависеть от того, помогает ли он выпускать больше качественного ПО при меньших общих расходах, а не только удешевляет выполнение теста. Независимые данные показывают, что координация моделей GitHub может приблизиться по результатам к ведущему агенту для программирования при примерно вдвое меньшей измеренной стоимости задачи. Проверка для команд — сохраняется ли это преимущество с учётом проверки кода, управления доступом, надёжности и полного цикла выпуска изменений.
