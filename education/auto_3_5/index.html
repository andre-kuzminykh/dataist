Как данные движутся по воркфлоу от шага к шагу

Потоки данных и маппинг, преобразование, маршрутизация, циклы и пакеты, ожидание, воркфлоу как инструмент

В автоматизации важны не блоки на схеме, а данные, которые проходят между ними. В материале разберём, как шаги передают друг другу данные и почему ошибки прячутся в маппинге, зачем данные преобразуют, чем ветвление отличается от разветвления и объединения и как циклы, пакеты и ожидание управляют ходом процесса. А в конце — как целый бизнес-процесс становится навыком агента.

Что движется по схеме

Воркфлоу — это движение данных между шагами.

У каждого шага есть контракт из трёх частей: входные данные, операция с параметрами и результат. Этот результат становится входом следующего шага. Например, на вход приходит номер заказа, шаг находит по нему клиента в CRM и возвращает объект клиента. Следующий шаг должен отправить этому клиенту письмо.

Данные между шагами обычно передаются в формате JSON. Чтобы следующий шаг взял из них нужное значение, используют переменные и выражения — так значение поля customer.email из объекта клиента подставляют в поле получателя письма. Такое связывание называют маппингом данных.

Именно на маппинге часто возникают ошибки.

Один блок ищет клиента, другой отправляет письмо — каждый по отдельности работает правильно. Но во второй блок приходит не то поле, не тот объект или не тот тип данных.

Каждый блок работает — а данные не те
🏷️ Не то поле в получателе "Анна" — имя вместо почты
👤 Не тот объект в получателе "менеджер@почта.рф" — почта, но не клиента
🧺 Не тот тип в получателе [ "анна@почта.рф" ] — адрес верный, но это массив вместо строки
Главный вопрос отладки:
откуда на этом шаге взялось каждое значение?
Все три ошибки живут в связи между шагами, и искать их нужно в маппинге

Поэтому главный вопрос при отладке — откуда именно на этом шаге взялось каждое значение. Ответ ведёт по цепочке назад, к шагу, который это значение вернул. Если вы не понимаете, как движутся данные, вы фактически не контролируете воркфлоу.

Данные приходят не в том виде

Даже идеальный ИИ-агент бесполезен, если следующий шаг получает данные в неправильном формате.

В реальных системах данные почти никогда не переходят между сервисами в идеальном виде. Где-то дата хранится строкой, а следующему сервису нужен другой формат. Телефон приходит с пробелами или с разными кодами страны. Сумма — строкой с пробелом, запятой и знаком рубля.

Одно значение — две формы
ПолеПришлоНужно следующему шагу
📅 Дата «03/07/24» 2024-07-03 — единый формат даты
📞 Телефон «8 916 123 45 67» +79161234567 — без пробелов, с кодом страны
💰 Сумма «12 000,00 ₽» 12000.00 — число вместо строки
Смысл значения прежний. Меняется форма, в которой его прочитает следующий шаг

Значительная часть воркфлоу — это преобразование данных: поля переименовывают, меняют их типы, нормализуют даты, очищают текст и удаляют лишнее. Иногда массив нужно разделить на отдельные записи, а иногда наоборот — собрать сотни записей в один объект. Сюда же относятся фильтрация, сортировка, удаление дубликатов и агрегация — например, сумма заказов или группировка клиентов по сегментам.

Три группы преобразований
🧹 поля и значения Привести в порядок Переименовать поля, изменить типы, нормализовать даты, очистить текст, удалить лишнее Цель — ожидаемый формат каждого значения
✂️ форма набора Разделить или собрать Массив — на отдельные записи или, наоборот, сотни записей — в один объект Цель — нужная структура для следующей операции
📊 состав и порядок Отобрать, упорядочить, свести Фильтрация, сортировка, удаление дубликатов, агрегация Цель — нужные записи или сводка: сумма заказов, группировка клиентов по сегментам
Операции разные, а задача одна: следующий шаг получает данные в том виде, который он ожидает

На преобразовании данных ломаются многие реальные процессы. Агент может правильно решить остановить платёж. Но если следующий шаг получил сумму строкой в неожиданном формате, вся работа агента становится бесполезной. Поэтому преобразование данных — основа надёжной автоматизации.

Маршрутизация данных

Автоматизация — не всегда цепочка шагов. Иногда она начинает ветвиться.

Как только процесс перестаёт быть прямым, появляется маршрутизация — нужно решить, куда данные пойдут дальше. Самый простой вариант — ветвление по условию. Если критерий выполнен, данные идут по одной ветке, если нет — по другой. Если вариантов несколько, выбирается один из них.

Ветвление важно не путать с разветвлением на несколько параллельных действий. Здесь система не выбирает одну ветку, а отправляет результат сразу в несколько направлений. Например, после обработки заказа нужно одновременно обновить CRM, создать задачу для доставки и отправить уведомление клиенту.

Выбрать одну ветку или запустить все
🔀 Ветвление · выбирает маршрут

Условие: критерий выполнен — одна ветка, не выполнен — другая.

Если вариантов несколько, срабатывает один из них. Остальные ветки не запускаются.

📣 Разветвление · запускает все

Выбора нет: результат уходит сразу в несколько направлений.

Заказ обработан — обновить CRM, создать задачу для доставки, уведомить клиента.

На схеме оба случая — несколько стрелок из одного блока. Различает их число веток, которые запустятся

Объединение используют, если результаты веток потом нужно снова собрать вместе.

Заказ обработан → три ветки → итог
🗂️ Обновить CRM ветка обновляет запись клиента
🚚 Создать доставку ветка создаёт задачу на доставку
🔔 Уведомить клиента ветка отправляет уведомление
Объединение: результаты трёх веток → общий итог по заказу
Ветки делают каждая свою часть работы, а объединение снова сводит их результаты в одну линию процесса

Ветвление выбирает маршрут, разветвление запускает несколько направлений, а объединение соединяет результаты. Параллельные ветки на схеме при этом не всегда выполняются одновременно — это зависит от среды исполнения. Схема показывает, что должно произойти, а в каком порядке это произойдёт на деле, решает среда.

Тысяча клиентов и один договор

Реальная автоматизация далеко не всегда идёт по прямой.

Что делать, если нужно обработать тысячу клиентов, дождаться человека и потом продолжить процесс?

Цикл повторяет одно действие для множества объектов. Но отправлять тысячу запросов одновременно — плохая идея: можно упереться в ограничения или перегрузить сервис. Поэтому данные разбивают на пакеты — например, по сто клиентов за раз.

Тысяча клиентов: волной или пакетами
Одной волной
👥 1000 клиентов 🌊 1000 запросов сразу ⛔ Ограничения, перегрузка сервиса
Процесс упирается в ограничения или перегружает сервис
Цикл пакетами
👥 1000 клиентов 📦 По 100 за раз 🔁 Десять проходов цикла
За раз к сервису уходит сто запросов вместо тысячи
Для каждого клиента выполняется то же действие, меняется только нагрузка на сервис

Другой сценарий — ожидание человека. Система отправила договор на согласование, и без ответа идти дальше не может. Она сохраняет текущее состояние, останавливается, а после ответа продолжает работу с нужного места. Как среда исполнения держит такую паузу, мы разбирали в статье о платформе.

Четыре приёма управления воркфлоу
🔁 много объектов Цикл Повторяет одно действие для множества объектов Одно действие — для каждого из тысячи клиентов
📦 нагрузка Пакеты Тысячу клиентов делят на части и обрабатывают по сто за раз Не упереться в ограничения и не перегрузить сервис
⏳ ответ человека Ожида­ние Договор ушёл на согласование: состояние сохранено, процесс ждёт человека Продолжить с нужного места
🧩 сборка из частей Подпро­цесс Проверку клиента выносят в отдельный небольшой процесс Одна проверка — для продаж, финансов и поддержки
Цикл и пакеты справляются с объёмом, ожидание — с паузой, подпроцесс — с повторяющимися частями: у каждого приёма своя задача

Процесс как навык агента

Большие процессы лучше разбивать на небольшие подпроцессы.

Подпроцесс создают один раз и подключают там, где он нужен. Например, проверку клиента можно использовать в продажах, финансах и поддержке.

Если агент может запускать такой подпроцесс сам, получается воркфлоу как инструмент — целый бизнес-процесс становится навыком агента. Агент вызывает готовую проверку клиента так же, как любой другой инструмент. Так сложные системы собираются из небольших переиспользуемых компонентов.

Шаги связывает маппинг

Откуда на этом шаге взялось каждое значение? Каждый блок может работать правильно, а следующий всё равно получит не то поле, объект или тип.

Даты, телефоны и суммы приходят не в том формате. Без преобразования верное решение агента не доходит до действия.
