# Исследования помогли улучшить ИИ-агентов без переобучения моделей

## Ограничения нынешних оптимизаторов

За последний год фреймворки для автоматической оптимизации обвязки агента в основном развивались по двум направлениям. Инструменты для отдельных компонентов — например, WikiSkill от Google, SkillOpt от Microsoft и Memento-Skills — анализируют действия агента и улучшают одну часть системы: библиотеку навыков или хранилище памяти.

Полноценные оптимизаторы обвязки, такие как DarwinX от Salesforce, HarnessX от Xiaomi, Self-Harness и Meta-Harness от Стэнфорда, используют мета-агента для программирования. Он изучает записи неудачных запусков и переписывает вспомогательный код или правила работы агента.

По мнению исследователей из Калифорнийского университета в Санта-Барбаре и Microsoft, методы, основанные только на обратной связи от выполнения задач, замыкаются в контур, где быстро снижается отдача.

Во-первых, мета-агент ограничен знаниями, заложенными в базовую модель. Исследователи отмечают: механизмы, которые предлагает мета-агент, зависят от знаний и способности к рассуждению его базовой модели. Запись неудачного запуска может выявить нехватку какой-то способности, но почти не подсказать, как её развить.

Когда мета-агент для программирования видит в записи повторяющиеся ошибки при вызове инструментов, он часто прибегает к знакомым приёмам — например, добавляет этап проверки или цикл обсуждения между несколькими агентами. В одном из примеров система заметила повторные ошибки при поиске и вызовах инструмента Python и добавила модуль условной проверки каждого действия. Проверяющий модуль отсеивал ошибочные вызовы, но стал чрезмерно осторожным и блокировал корректные запросы к API, необходимые для выполнения задачи.

Во-вторых, развитие на основе записей действий реагирует на уже произошедшие сбои. Исследователи пишут, что такой подход опирается на ситуации, с которыми система уже сталкивалась. Поэтому в рабочей среде слабое место агента может затронуть пользователей ещё до того, как накопится достаточно данных для полезного обновления.

Эти ограничения привели исследователей к вопросу: как опытный исследователь обнаружил бы улучшения, которые ещё не проявились в собственном опыте агента?

## Как устроен ScholarEvolve

ScholarEvolve анализирует сбои на обучающей выборке, ищет в научной литературе подходящие решения, реализует их в модулях обвязки и проверяет, как они работают вместе.

Чтобы изменение одной части агента не нарушало работу другой, фреймворк делит обвязку на пять модулей с чётко заданными входами и выходами: интерфейс инструментов, управление контекстом, навыки, память и рабочие процессы агента.

Пайплайн оптимизации состоит из четырёх этапов:

1. **Анализ сбоев и поиск литературы.** Модель-аудитор изучает неудачные задачи из обучающей выборки и выявляет общие пробелы в способностях — например, потерю прежних наблюдений или неспособность исправить синтаксическую ошибку. Затем она формирует поисковые запросы и находит подходящие статьи и аннотации на arXiv.
2. **Тематическая группировка для разнообразия поиска.** Чтобы не находить похожие статьи, ScholarEvolve применяет метод тематического моделирования TopicGPT. Он группирует работы по семействам механизмов внутри каждого модуля. Затем фреймворк использует разные механизмы, чтобы агент для программирования проверял разные инженерные идеи.
3. **Планы изменений и проверки работоспособности.** Для каждой выбранной статьи исследовательский агент изучает полный текст и доступный официальный код, а затем составляет план изменений. Агент для программирования реализует его на Python в одном модуле, оставляя остальные четыре без изменений. Автоматические проверки подтверждают, что новый код импортируется без ошибок, соблюдает контракты интерфейсов и формирует допустимые действия, прежде чем начнётся полная оценка.
4. **Сочетание модулей и отбор.** После оценки отдельных обновлений на проверочной выборке ScholarEvolve с помощью генетического скрещивания объединяет лучшие модули в полные варианты обвязки. Каждый вариант проходит совместное регрессионное тестирование на проверочных задачах, а статистическая проверка допускает замену текущего лучшего варианта только при подтверждённом улучшении.

На Qwen3.5-27B в среде AppWorld ScholarEvolve получил три заметных улучшения:

- **Исправление ошибочных вызовов API — интерфейс инструментов.** Исходный агент часто генерировал неправильный синтаксис Python или угадывал параметры API, не проверяя документацию. ScholarEvolve использовал метод из статьи ToolACE-R: добавил проверку абстрактного синтаксического дерева для вызовов Python перед их выполнением, а также макрос, который разворачивается в код Python и выводит документацию API по запросу.
- **Сохранение прежних наблюдений — управление контекстом.** Длинная история взаимодействия могла превышать доступный объём контекста или мешать агенту учитывать предыдущие данные. Опираясь на работу об ограничениях сжатия промтов, фреймворк создал модуль распределения бюджета с учётом запроса. Он оставляет системные правила без изменений, оценивает историю разговора по актуальности для задачи и давности, распределяет доступный объём символов и сохраняет хронологический порядок.
- **Повторное использование последовательностей API — навыки.** Вместо того чтобы заново находить многошаговые вызовы API при каждом запуске, ScholarEvolve применил подход из статьи Skill-as-Pseudocode. Он обнаружил повторяющиеся последовательности API в успешных обучающих запусках и собрал из них типизированные шаблоны псевдокода.

## Результаты испытаний

Исследователи проверили ScholarEvolve на двух интерактивных бенчмарках, имитирующих некоторые корпоративные процессы. В AppWorld агенты пишут код и вызывают API нескольких приложений. В tau-Bench Telecom они вместе с имитируемым пользователем решают проблемы с обслуживанием клиентов, мобильным интернетом и сообщениями. Исследователи улучшили базовую обвязку моделей Qwen3.5-27B и GPT-5.4-mini, а затем сравнили результат с исходными обвязками, Meta-Harness от Стэнфорда и набором передовых моделей.

ScholarEvolve улучшил обе базовые модели по всем проверенным показателям. В AppWorld показатель выполнения целей задачи (TGC) у Qwen3.5-27B вырос на 12,4 процентного пункта, а показатель выполнения целей сценария (SGC) — на 20,2 пункта. Для SGC нужно успешно пройти три варианта одного сценария. В Telecom результат GPT-5.4-mini вырос с 72,7% до 81,9%.

Исследователи отмечают, что обвязка заметно влияет на способности, которые может проявить базовая модель.

В экспериментах для корпоративных команд выделились несколько результатов:

- **Работа с незнакомыми приложениями и сложными API без дополнительных примеров.** В AppWorld Challenge агенты работают с API Amazon и Gmail, которых нет в обучающей и проверочной выборках оптимизации. С улучшенной обвязкой результат Qwen3.5-27B вырос с 49,6% до 63,6% — на 14 процентных пунктов. Это на 9 пунктов выше результата Meta-Harness.
- **Почему оценка отдельного модуля может ввести в заблуждение.** В исследовании с исключением компонентов обновлённый модуль навыков для Qwen3.5-27B отдельно набрал 75,4%, а модуль Skill-as-Pseudocode — 73,7%. Но в сочетании с улучшенными модулями инструментов, контекста, памяти и рабочих процессов второй модуль дал более сильную систему: 84,8% против 80,7% выполненных задач. Авторы заключают, что результаты отдельных модулей сами по себе не позволяют определить лучшее сочетание.
- **Исправление ошибок в середине задачи.** В рабочей среде вызовы инструментов неизбежно завершаются ошибками. Надёжность агента зависит от того, как он реагирует на сообщения об ошибках. В AppWorld Challenge среди запусков, где возникала промежуточная ошибка выполнения Python, улучшенная обвязка Qwen3.5-27B завершила задачу в 59,9% случаев, а исходная — в 44,9%. Исследователи поясняют, что ошибка инструмента сама по себе не показывает всех способностей агента: для многих успешных задач нужно использовать полученное сообщение об ошибке, чтобы изменить дальнейшие действия.

## Что учитывать корпоративным командам

Исследователи указали ссылку на репозиторий GitHub, но на момент публикации он был пуст. В приложениях к статье приведены фрагменты кода для пяти выбранных модулей обвязки. Поскольку веса базовой модели в ходе процесса остаются замороженными, инженерным командам не нужно управлять отдельными контрольными точками модели.

ScholarEvolve находит статьи и доступный официальный код, связанный с исследованиями. Автоматические проверки фреймворка оценивают возможность импорта кода Python, совместимость интерфейсов, создание артефактов и корректность формата действий. При этом в статье не описана проверка найденных статей и стороннего кода на вредоносные зависимости, небезопасные способы выполнения или уязвимости к внедрению промтов.

Корпоративным командам не следует разрешать мета-агенту внедрять в рабочую среду непроверенный код, созданный на основе исследований. Вместо этого можно создать шлюз проверки безопасности или направить фреймворк на курируемый внутренний репозиторий проверенных статей и инженерных проектных документов.

Развитие обвязки решает не все проблемы в пайплайне агента. Оно может улучшить форматирование ответов, распределение бюджета контекста и восстановление после ошибок API, но не заменяет детерминированные ограничения на уровне шлюза API и не исправляет слабые дата-пайплайны поиска информации на предыдущих этапах.

Исследователи также проверили три последовательных раунда обновлений на основе литературы, не меняя веса Qwen и ранее собранные данные о задачах. Результат на AppWorld Normal улучшался после каждого раунда. Однако эксперименты не проверяли непрерывную адаптацию в рабочей среде.

По словам исследователей, обновления на основе литературы позволяют заранее адаптировать агента: новые публикации могут подсказать улучшения ещё до того, как соответствующие сбои проявятся при работе с пользователями. Например, развёрнутый агент мог бы ежемесячно изучать свежие исследования и проверять перспективные обновления на проверочных задачах.
