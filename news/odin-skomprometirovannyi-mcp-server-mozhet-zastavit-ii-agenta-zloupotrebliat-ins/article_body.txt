# Один уязвимый MCP-сервер может направить ИИ-агента против доверенных инструментов

## Как менялись правила авторизации MCP

История авторизации MCP состоит из пяти этапов, отражённых в официальных журналах изменений спецификации:

1. Сначала у протокола не было общей схемы авторизации: её полностью оставили на усмотрение разработчиков.
2. Затем добавили комплексную схему авторизации на основе OAuth 2.1.
3. MCP-серверы определили как полноценные серверы ресурсов OAuth. Также ввели обязательные индикаторы ресурсов (RFC 8707), чтобы вредоносные серверы не могли получать токены, предназначенные для других служб.
4. В качестве рекомендуемого способа регистрации добавили документы метаданных идентификатора клиента OAuth (CIMD), наряду с динамической регистрацией клиентов (DCR).
5. DCR объявили устаревшим и заменили на CIMD. Клиенты должны проверять параметр `iss` (RFC 9207). Этот этап назвали крупнейшим обновлением со времени запуска MCP.

В первой версии MCP вообще не было требований к аутентификации. С тех пор каждое обновление добавляло более строгие правила. Поэтому серверы, созданные в первый год существования протокола, могут опираться на подходы, которые уже не соответствуют спецификации. Направление изменений — переход к формальным механизмам OAuth вместо облегчённых схем регистрации, выбранных самими разработчиками.

## На что указывают OWASP и АНБ США

В перечне OWASP MCP Top 10 неправильное управление токенами и утечки секретов отнесены к наиболее серьёзным рискам. Жёстко заданные учётные данные и секреты, сохранённые в памяти модели, могут открыть доступ ко всей подключённой среде. В некоторых случаях их удаётся извлечь с помощью промт-инъекции.

В рекомендациях АНБ США за май 2026 года отмечено, что лишь две из десяти категорий риска OWASP связаны с текстом, который агент читает и обрабатывает. Остальные восемь, включая риски для учётных данных, области доступа и идентификации, относятся к инфраструктуре, которую MCP никак не ограничивает встроенными средствами. Протокол стандартизировал обнаружение инструментов и вызовы к ним, но не определил, как проверять вызывающую сторону и устанавливать, к чему ей разрешён доступ.

## Как распространяется атака

Unit 42, подразделение Palo Alto Networks, проверило сценарий с подключением пяти MCP-серверов к одному ИИ-агенту. В испытаниях успешными оказались 78,3% атак. Пять серверов — обычный масштаб для команды, которая уже вышла за пределы единственного пробного проекта.

Риск связан с цепочкой доверия. Если агент принимает данные одного сервера за надёжный контекст, скомпрометированный сервер может внедрить инструкции, которые попадут в последующие вызовы инструментов. Под угрозой оказываются и серверы, которые сами не были взломаны.

## Два сценария развёртывания

Для внутреннего инструмента за корпоративным экраном риск ниже, но не исчезает. В блоге Inside Track Microsoft описала правила управления внутренними MCP-системами: даже для трафика внутри компании там используют короткоживущие токены с минимально необходимыми правами. Внутренний доступ, согласно этому подходу, не означает автоматически доверенный доступ.

Для удалённого сервера или многопользовательской облачной службы, которая открывает точку подключения клиентам, ставки выше. В рекомендациях Microsoft для Azure предлагается использовать шлюз с проверкой идентификаторов: он должен отклонять вызовы без действительного токена, привязанного к нужной аудитории. Кроме того, реестр должен фиксировать определения инструментов. Так незаметное изменение поведения доверенной зависимости — атака типа «подмена зависимости» — обнаруживается по отклонению от зафиксированного состояния, а не уже после запуска в рабочей среде.

## Что делать и чего избегать

**Рекомендуется:**

- Рассматривать каждый MCP-сервер как сервер ресурсов OAuth, который проверяет токены: именно в эту сторону спецификация движется с июня 2025 года.
- Ограничивать область действия токенов и задавать им короткий срок жизни. Microsoft отдельно предупреждает против выдачи полного доступа к почтовому ящику, если достаточно прав только на чтение.
- Уже сейчас проверять параметр `iss`, не дожидаясь, пока это требование станет обязательным.

**Не рекомендуется:**

- Считать DCR надёжным решением на долгий срок: с июля 2026 года этот механизм официально устарел.
- Загружать учётные данные при запуске сервера и хранить их вместо получения при каждом вызове. Токен в памяти процесса нельзя по-настоящему отозвать.
- Подключать новый MCP-сервер, не регистрируя его в системе, где подключениями можно управлять.

## Где применять контроль

Вопрос о централизованной или индивидуальной проверке каждый раз решается в пользу отдельного уровня перед серверами. Microsoft и АНБ США независимо пришли к одному подходу: проверку идентификаторов, области доступа и журналирование следует вынести на такой уровень, а не полагаться на каждый сервер по отдельности. Шлюз может закреплять определения инструментов и сообщать об их изменениях.

## Проектировать с учётом изменений

Схема авторизации MCP менялась в каждом обновлении протокола, а дальнейшее усиление защиты уже обозначено. При этом направление остаётся стабильным: формальные схемы серверов ресурсов, явная проверка издателя токена и централизованное управление вместо неформального доверия. Для технического директора, который планирует подключить новый MCP-сервис, управление идентификаторами и доступом — часть самого проекта, а не дополнительная задача после запуска.

По оценке Dataist, распространение MCP делает управление доступом общим инфраструктурным вопросом: ошибка одного сервера может затронуть вызовы к другим подключённым инструментам. При этом спецификация пока не задаёт встроенных ограничений для многих ключевых рисков, поэтому безопасность зависит от того, как компании организуют проверку токенов, регистрацию серверов и контроль изменений.
